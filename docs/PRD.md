| 项目 | 内容 |
|---|---|
| 文档版本 | v0.2-design-baseline |
| 基准日期 | 2026-09-03 |
| 当前阶段 | Phase 1 产品与技术设计 |
| 产品形态 | 管理端、企业操作端、消费者响应式 Web 页 |
| 目标版本 | 教学演示 MVP v0.1.0 |

## 1. 文档目的

本文定义冷冻海产品溯源系统首个可验收版本的范围、业务规则和质量标准，是后续原型、数据库、接口、代码和测试的共同基线。旧“肉类食品溯源”资料只用于理解批次追踪、上下游确认和三端划分，不构成本项目正式需求。

## 2. 背景与问题

冷冻海产品从捕捞、养殖或进口来源进入供应链后，可能经历收购、加工速冻、分装、合批、冷库、运输、经销和零售。现有参考项目将供应链固定为“养殖—屠宰—批发—零售”，使用多张节点批次表，无法准确表达海产品的加工、拆分、合并和冷链温度，也缺少异常处置、召回和审计。

本项目要解决的核心问题是：以批次为最小追溯单元，把跨企业的关键业务事件和证据连接成可查询的批次谱系，使来源可查、去向可追、异常可定位、责任操作可审计。

## 3. 产品定位与真实性声明

一句话定义：面向冷冻海产品供应链参与方、质量人员和消费者，以“批次 + 追溯事件 + 批次关系”为核心，提供一码查询、正反向追溯、冷链异常处置和模拟召回。

产品必须始终明确：

- 系统证明的是“谁在何时记录了什么”，不能仅凭企业自填数据证明货物真实或合规。
- 二维码用于查询，不等同于防伪码。
- MVP 的温度数据可手工录入或由模拟器生成，页面必须展示数据来源。
- 检测报告只记录摘要和演示附件，不验证检测机构或证照真伪。
- 召回功能用于流程演示，不替代真实企业的法定报告和处置程序。

## 4. 产品目标

### 4.1 业务目标

1. 企业操作员能够为一个冷冻海产品批次建立连续电子履历。
2. 质量人员能够从问题批次反向查来源、正向查去向，并形成异常处置记录。
3. 消费者扫描二维码后能够看到经过筛选和脱敏的产品来源与流通信息。
4. 教师能够依据 PRD、Issue、PR、测试和发布记录，检查完整的软件工程过程。

### 4.2 成功标准

- 至少 3 条预置演示链能够端到端查询。
- 同时覆盖批次拆分与合并，不把供应链简化为单一线性列表。
- 温度越界和检测不合格均能触发可闭环处理的异常。
- 企业间数据隔离、消费者字段脱敏和关键写操作审计通过验收测试。
- 干净环境依据 README 能够完成初始化、运行和演示。

## 5. 范围

### 5.1 MVP 范围

- 预包装冷冻海水鱼、虾蟹、贝类、头足类等动物性海产品演示数据。藻类、调理食品和即食水产制品需另建适用标准矩阵，本期不纳入。
- 来源类型支持国内捕捞、国内养殖、进口三类；进口资料在 MVP 中仅人工登记，不接海关接口。
- 覆盖来源/采购、加工与速冻、仓储、运输、企业交接、检测、销售、查询和模拟召回。
- 使用批次级追溯。包装单元可以共享批次追溯码，本期不做逐件防伪。
- 企业端采用统一业务模型，通过组织类型、场所类型和事件类型区分供应链环节。

### 5.2 本期不做

- 真实区块链、电子签章或硬件级不可篡改。
- 真实 IoT 设备、海关、政府监管、物流公司和检测机构接口。
- 商城、支付、结算、财务或完整库存 ERP。
- 车辆实时定位、路线优化、AI 风险预测。
- 原生移动 App；消费者使用手机浏览器页面。
- 生产环境合规认证和真实食品召回执行。
- 活体、冰鲜、淡水产品的专门业务规则。

## 6. 用户与权限

| 角色 | 数据范围 | 核心权限 |
|---|---|---|
| 系统管理员 | 全平台 | 组织、用户、角色、基础字典、产品类别和规则配置 |
| 企业操作员 | 本组织 | 批次建档、业务事件、交接、温度、附件和本组织查询 |
| 企业质量管理员 | 本组织及被授权关联链 | 检测审核、告警处理、冻结、模拟召回、处置记录 |
| 审计查看者 | 被授权范围，只读 | 跨组织追溯、审计日志和统计查询 |
| 消费者 | 公开字段，无需登录 | 按追溯码查询可公开信息和召回提示 |

业务中的捕捞/养殖主体、加工厂、冷库、承运商、经销商和零售商是“组织类型”，不各自复制一套登录、列表和批次表。实训 MVP 将企业主要负责人、食品安全总监和食品安全员的细分职责合并为“企业质量管理员”，但审批记录应保留岗位类型、审批人和履职时间，便于后续扩展。

## 7. 核心业务模型

### 7.1 主流程

```mermaid
flowchart LR
    A[来源批次建档] --> B[加工/速冻事件]
    B --> C[拆分或合并]
    C --> D[冷库入库/出库]
    D --> E[冷链运输]
    E --> F[接收方验收确认]
    F --> G[经销/零售]
    G --> H[生成或启用公开追溯码]
    H --> I[消费者查询]
```

### 7.2 异常闭环

```mermaid
flowchart LR
    A[温度越界/检测不合格] --> B[生成告警]
    B --> C[质量人员确认]
    C --> D[冻结受影响批次]
    D --> E[正向追踪与反向溯源]
    E --> F[发起模拟召回]
    F --> G[记录通知、回收与处置结果]
    G --> H[复核后关闭]
```

### 7.3 状态规则

批次状态：`DRAFT`（草稿）→ `ACTIVE`（正常流转）→ `FROZEN`（业务冻结）→ `RECALLED`（召回中/已召回）→ `CLOSED`（关闭）。

交接状态：`DRAFT` → `PENDING` → `ACCEPTED` 或 `REJECTED`。

告警状态：`OPEN` → `ACKNOWLEDGED` → `PROCESSING` → `RESOLVED` 或 `DISMISSED`。

状态约束：

- 草稿可以编辑和删除；已提交事件不得物理删除。
- 已提交记录有误时新增“更正记录”，保留原值、修改人、时间和原因。
- 冻结或召回批次不得继续发货、接收或生成新的销售批次。
- 交接只有接收方确认后才完成；拒收必须填写原因。
- 批次关系不得形成环，拆分/合并必须保留投入数量和单位。

优先级含义：P0 为 MVP 必须完成，P1 为时间允许时完成，P2 为后续版本。

| FR-ORG-001 | P0 | 组织、场所、用户与基础字典管理 | 管理员可维护；停用对象不能产生新业务 |
| FR-PROD-001 | P0 | 产品主数据与温控规则 | 可记录品名、物种/规格、来源类型、储存温度范围和单位 |
| FR-BATCH-001 | P0 | 创建和维护批次 | 生成内部 ID 与不可猜测的公开追溯 ID；批次号按组织唯一 |
| FR-BATCH-002 | P0 | 批次拆分、合并和加工转换 | 可建立多对多谱系；阻止循环关系；校验同单位数量合理性 |
| FR-EVENT-001 | P0 | 关键追溯事件 | 支持来源、采购、加工、速冻、包装、入库、出库、运输、到货、销售事件 |

| FR-QA-001 | P0 | 检测报告摘要 | 保存检测机构名称、日期、项目、结论和附件；不合格可触发告警 |
| FR-TRACE-001 | P0 | 企业端正反向追溯 | 从任意批次遍历全部上游、下游和关键事件，支持拆分/合并 |

## 9. 核心字段与实体

| 实体 | 关键字段 |
|---|---|
| Organization | 组织编号、名称、类型、统一社会信用代码（演示值）、状态 |
| Site | 所属组织、名称、地址、场所类型、时区 |
| User / Role | 用户、所属组织、角色、状态、最后登录时间 |
| Product | 品名、学名可空、品类、规格、来源类型、温度上下限、单位、规则版本 |
| Batch | 内部 ID、业务批次号、公开追溯 ID、产品、数量、单位、当前组织、来源、生产/捕捞/冻结日期、保质期、状态 |
| BatchRelation | 上游批次、下游批次、拆分/合并/加工类型、投入数量、产出数量 |
| TraceEvent | 批次、事件类型、业务发生时间、系统录入时间、组织、场所、操作人、数据来源、状态、备注 |
| Transfer | 发货/收货组织、批次、数量、运输任务、发货时间、签收时间、确认状态 |
| Shipment | 承运组织、车辆/箱号、起止地点、装卸时间、要求温区 |
| TemperatureRecord | 批次或运输任务、测量时间、温度、单位、数据来源、设备号可空、规则版本 |
| InspectionReport | 批次、机构名称、日期、项目摘要、结论、报告编号、附件 |
| Alert | 类型、批次、严重度、触发规则、状态、处理人、处理结论 |
| Recall | 原因、等级、适用规则版本、范围、关联批次、涉及/库存/在途/已售/通知/退回/处置数量、通知摘要、状态、处置结果 |
| RecallPolicy | 规则版本、生效日期、风险等级、启动时限、完成时限、过程报告周期 |
| Attachment | 文件名、类型、大小、哈希、访问级别、关联对象 |
| AuditLog | 操作人、组织、动作、对象、发生时间、变更前后摘要、请求标识 |

数据设计硬约束：

- 内部主键与公开追溯 ID 分离，禁止在二维码中暴露自增主键。
- 同时保存业务发生时间和系统录入时间，补录不伪装成实时采集。
- 所有测量值必须带单位，温控规则按产品或任务配置并保留版本。
- 加工数量至少满足“投入 = 产出 + 损耗 + 废弃 + 留样”的可解释平衡；发生单位换算时记录换算规则。
- 已提交追溯事件采用追加式更正，不允许静默覆盖。
- 消费者接口使用公开字段白名单，不能直接序列化内部实体。
- 生产记录和关键凭证不在业务界面中物理删除；保留期限在详细设计阶段按适用法规配置。

## 10. 消费者查询页

公开展示：

- 产品名称、品类、规格、批次号的公开形式。
- 来源类型和经过脱敏的产地/海域/原产国。
- 加工、速冻、仓储、运输、交接、检测和销售的关键时间线。
- 温控要求、温度记录摘要、数据来源说明和异常处置结论。
- 当前批次状态、召回提示和查询时间。

不得公开：

- 登录账号、操作员姓名、手机号、身份证明、内部备注。
- 企业证照原件、检测报告原件的非公开信息。
- 精确设备密钥、内部数据库 ID、访问令牌和系统拓扑。

## 11. 非功能需求

### 11.1 安全与隐私

- 密码使用经过评审的自适应哈希算法保存，严禁明文和可逆加密。
- 认证、授权和组织边界必须在服务端执行。
- 配置与密钥通过环境变量或密钥服务注入，不提交仓库。
- 上传文件限制扩展名、MIME、大小和访问级别，文件名由服务端重新生成。
- 演示数据虚构；消费者端按最小必要原则公开字段。
- 关键接口进行输入校验、统一错误处理和安全日志记录。

### 11.2 数据完整性与审计

- 数据库约束保证唯一性、引用完整性和状态合法性。
- 批次状态、批次关系、检测结论、告警、冻结和召回全部审计。
- 追溯图遍历必须检测循环并限制异常深度，防止错误数据拖垮查询。
- 数据来源枚举至少包含 `MANUAL`、`IMPORT`、`SIMULATED`、`DEVICE`；MVP 不得把前三者展示为设备实采。

### 11.3 性能基线

在统一测试环境中，以 1,000 个批次、10,000 条事件、20 个并发查询为实训基线：

- 批次详情和追溯查询 P95 不超过 2 秒。
- 消费者查询首屏 P95 不超过 3 秒。
- 普通表单保存和二维码生成 P95 不超过 2 秒。

这些指标用于课程验收，不代表生产容量承诺。

### 11.4 兼容性与易用性

- 支持验收时 Chrome、Edge 的当前稳定版。
- 消费者页适配最小 360px 宽度。
- 表单明确标出必填项、单位、时区和校验失败原因。
- 时间统一按 UTC 存储，按项目配置时区展示；导出文件带时区。

### 11.5 可维护性

- 核心追溯、权限、状态机和告警规则必须有自动化测试。
- 日志能够以请求标识关联用户、接口和业务对象。
- 数据库变更必须版本化，不允许只在个人数据库手工改表。
- 新环境按照 README 应在 30 分钟内完成依赖准备后的启动。

## 12. MVP 验收场景

1. 建立至少 3 条完整演示链，每条包含来源、加工/速冻、仓储、运输、交接和销售。
2. 一条链包含“一批拆多批”，另一条包含“多批合一批”，正反向结果与预置答案一致。
3. 每条链包含检测和温度数据，至少一条包含温度越界，数据来源清晰可见。
4. 温度越界自动生成告警，质量管理员可确认、冻结、处置并关闭。
5. 检测不合格后，系统能找出全部关联下游批次并发起模拟召回。
6. 消费者扫描有效码可查询公开履历；无效、停用、召回码进入对应状态页。
7. 企业操作员无法读取或修改无关联、未授权的其他组织数据；越权测试全部通过。
8. 按公开字段清单检查消费者接口，不泄露任何内部字段。
9. 关键写操作均可在审计日志定位到用户、组织、时间、对象和变更摘要。
10. 干净环境可按文档构建、测试并启动，CI 的必需检查全部通过。
11. 没有阻断主流程或造成越权、数据串组织的高严重度缺陷。
12. 功能编号、Issue、PR 和测试用例能够互相引用。

## 13. 里程碑（20 个工作日基线）

| 里程碑 | 时间 | 主要交付物 | 退出条件 |
|---|---:|---|---|
| M0 调研与范围冻结 | D1–D2 | 调研记录、术语、PRD、不做项 | 团队确认 P0 与待决项 |
| M1 产品与设计评审 | D3–D5 | 原型、权限矩阵、数据模型、接口草案、ADR | 关键流程和模型评审通过 |
| M2 最小纵向闭环 | D6–D10 | 建批次→记事件→追溯码→公开查询 | 前后端端到端跑通 |
| M3 追溯与风险闭环 | D11–D15 | 拆分/合并、温度、检测、告警、召回、审计 | P0 业务场景通过 |
| M4 联调与验收 | D16–D18 | 测试报告、性能基线、安全检查、缺陷清单 | 无阻断或高危缺陷 |

若实际周期更短，先移除 P1/P2，不能删掉权限隔离、审计和最小端到端闭环。

| 食品追溯应支持信息采集与留存 | 批次、事件、审计和正反向查询 | FR-BATCH-001、FR-EVENT-001、FR-TRACE-001 | TC-TRACE 系列 |

| 冷链需记录运输、仓储、装卸与异常 | 温度、运输任务、告警及处置 | FR-COLD-001、FR-RISK-001 | TC-COLD 系列 |
| 市场销售需查验进货和供货信息 | 企业交接确认、凭证摘要 | FR-TRANSFER-001、FR-QA-001 | TC-TRANSFER 系列 |
| 问题食品需停止经营、追踪流向和召回 | 冻结、正向追踪、模拟召回 | FR-TRACE-001、FR-RISK-001 | TC-RECALL 系列 |
| 个人信息处理应最小必要 | 公开字段白名单和权限校验 | FR-AUTH-001、FR-TRACE-002 | TC-AUTH、TC-PUBLIC |

## 15. 风险与控制

| 风险 | 控制措施 |
|---|---|
| 直接替换旧肉类项目名词 | 采用通用批次、事件、批次关系模型，删除肉类专属角色和证件 |
| 范围持续膨胀 | 冻结 P0；新增需求必须走变更评审并说明替换的工作量 |
| 自填信息被误解为真实证明 | 页面标注数据来源和演示属性，不宣传防伪或真实性背书 |
| 把 -18℃ 写死给全部产品 | 温度按产品/任务配置，保存规则版本和单位 |
| 只支持线性时间轴 | 数据模型和测试同时覆盖拆分、合并、循环阻止 |
| 历史被覆盖或删除 | 已提交记录追加式更正，关键变化进入审计日志 |
| 二维码泄露内部数据 | 不可猜测公开 ID、字段白名单、接口安全测试 |
| 技术版本沿用过旧模板 | 架构评审时核对课程硬约束并形成 ADR，不盲用 MySQL 5.5/Vue CLI |
| 参考资料版权风险 | 原始 DOCX、PNG、Axure 文件只留本地并由 `.gitignore` 排除 |

## 16. 待确认项

以下问题不阻碍仓库初始化，但必须在 M0 评审中明确：

1. 实训准确工期、团队人数和每位成员职责。
2. 教师是否强制 JDK 8、MySQL 5.5、Vue CLI，以及是否允许使用更安全的新版本。
3. MVP 演示是否必须包含进口冷冻海产品，还是仅做国内捕捞/养殖。
4. 是否要求还原旧原型的三个独立入口，或允许统一登录后按角色展示菜单。
5. 温度数据采用手工录入、CSV 模拟，还是教师提供设备/接口。
6. 二维码是否为硬性验收项；建议 P0 保留，因为它是消费者闭环入口。
7. 附件是否需要真实文件上传；建议首版只支持脱敏 PDF/JPG 演示文件。
8. 最终部署环境是个人电脑、学校服务器还是云主机。

## 17. 评审与变更

- v0.1 为讨论稿；团队评审通过后标记 v1.0-baseline。
- 范围基线后的新增、删除或业务规则变化必须创建需求变更 Issue。
- 变更 Issue 应说明原因、影响的功能编号、数据库/API/测试/文档影响、工作量和替换项。
- PRD、原型、接口和测试发生冲突时，先修正文档并完成评审，再实现代码。

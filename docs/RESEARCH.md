# 冷冻海产品溯源领域调研

检索基准：2026-09-03

## 1. 调研结论

1. 本项目应采用“批次 + 追溯事件 + 批次关系”的模型，而不是为每类企业分别建一张批次表。
2. 最小业务闭环不是普通 CRUD，而是来源建档、加工速冻、拆分/合并、冷库、运输、交接、检测、公开查询、异常处置和模拟召回。
3. 冷链温度必须连同测量时间、单位、采集来源和适用规则记录。演示可使用默认阈值，但不能把单一温度写死成所有产品的规则。
4. 追溯码只提供记录查询能力；没有可信采集、签章或第三方校验时，不能宣传为防伪或真实性证明。
5. 法规和标准用于推导功能与字段。未逐条获得、阅读标准全文并完成符合性测试前，只能写“参考设计”，不能写“完全符合国家标准”。

## 2. 术语和范围

| 术语 | 本项目定义 |
|---|---|
| 冷冻海产品 | 已冻结并需要温控流通的海洋动物性水产品；本期不专门覆盖活体、冰鲜和淡水产品 |
| 追溯单元 | 能够被唯一识别并沿供应链追踪的批次 |
| 追溯事件 | 在特定时间、地点、组织对批次实施的来源、加工、仓储、运输、交接、检测等行为记录 |
| 批次谱系 | 原料批次经拆分、合并、加工或分装形成的有向关系图 |
| 反向溯源 | 从当前批次查询全部上游来源 |
| 正向追踪 | 从问题批次查询全部下游去向和衍生批次 |
| 公开追溯码 | 面向消费者的不可猜测查询标识，不等同于数据库主键或防伪凭证 |

法规和国家标准常使用“水产品”“食用农产品”“动物性水产品”或“冷链食品”等更宽概念。本文只把其中适用于冷冻海产品供应链的要求映射到项目，不擅自扩大法律结论。

GB 31605-2020 给出的通用冷冻场景基准包括运输、贮存环境温度不高于 -18℃，并对自动记录间隔和冷库传感器布点提出要求。系统设计因此采用“规则版本 + 生效日期 + 产品适用范围”，保留采集间隔、设备位置和校准状态；实际判定还要服从产品标签、合同或更严格的企业标准，不能只在代码中写死一个温度。

标准状态会变化。进入系统设计、结题报告和答辩前，应再次在全国标准信息公共服务平台核验，并以正式标准全文而非搜索摘要为准。

## 4. 领域信息清单

### 4.1 来源信息

- 来源类型：国内捕捞、国内养殖、进口。
- 品名、品类、学名可空、规格等级。
- 捕捞海域/渔区、养殖场或原产国；进口场景可记录入境口岸。
- 捕捞、出塘或入境日期，来源组织和原始批号。
- 捕捞船/养殖主体/进口商标识；MVP 使用演示标识。
- 合格证明、检验检疫或承诺达标合格证等凭证的编号和摘要。

养殖水产品的承诺达标合格证可参考农业农村部对[《农产品质量安全承诺达标合格证管理办法》的官方解读](https://jgs.moa.gov.cn/gzdt/jgjdt/202512/t20251223_6480038.htm)。合格证制度的适用范围不能未经确认就强制套到所有野生捕捞或进口批次。

### 4.2 加工与冻结信息

- 原料批次与成品批次关系、投入/产出数量和单位。
- 加工企业、场所、加工方式、加工开始/结束时间。
- 冻结时间、冻结方式、包装日期、包装规格、净含量。
- 保质期、储存温度要求和适用规则版本。
- 检测报告编号、项目摘要、结论和受控附件。

### 4.3 仓储与运输信息

- 冷库、库位可空、入库/出库时间、经办组织。
- 运输单号、承运方、车辆/集装箱号、装货/卸货时间和地点。
- 目标温区、温度测量时间、值、单位、来源和设备号可空。
- 发货数量、收货数量、损耗/差异、交接确认与拒收原因。
- 超温、断档、延迟、包装破损等异常及处置结论。

### 4.4 销售与风险信息

- 供货者、收货者、进货/销售日期、数量和凭证摘要。
- 当前持有组织、公开追溯码状态和销售批次。
- 告警类型、严重度、触发规则、确认与处置记录。
- 召回原因、等级、上下游范围、通知摘要、回收数量和最终处置。

## 5. 旧“肉类食品溯源”资料评估

### 5.1 可以借鉴

- 管理端、企业操作端、消费者端的三类使用场景。
- 以批次而非单件作为追溯基础。
- 上下游批次关联、接收方确认和消费者追溯码查询。
- 登录、菜单、表单、列表、详情、分页和统计的通用交互结构。
- 用例的“场景—操作—事件—页面—验收”写法。

### 5.2 必须舍弃或重做

| 旧资料 | 不适用原因 | 新方案 |
|---|---|---|
| 养殖→屠宰→批发→零售固定链 | 冷冻海产品可能来自捕捞、养殖或进口，并经过多次加工、冷库和运输 | 组织类型 + 通用事件，可组合实际链路 |
| “两证两章”、动物检疫、肉品品质检验 | 属于肉类/屠宰特定业务 | 使用水产品来源、合格证明、检验检疫和检测摘要 |
| 每个节点一张批次表 | 无法自然表达拆分、合并、分装和多次加工 | 通用批次表 + 批次关系表 + 事件表 |
| 只有新建、确认、下架 | 无温度、检测、冻结、召回和更正闭环 | 独立的批次、交接、告警、召回状态机 |
| 查询只展示四家企业 | 信息不足，不能定位冷链和质量异常 | 展示来源、加工、温控、交接、检测和处置时间线 |
| 模板中的旧技术版本 | MySQL 5.5、Vue CLI 等已过时，且 Spring Boot 大版本与 JDK 有兼容边界 | 先确认课程硬约束，再以 ADR 锁定版本 |

参考文档中还存在复制残留、错别字和前后角色不一致，因此不能用“全文替换名词”的方式生成新需求。

## 6. 需求推导原则

- 一条法规/标准依据至少映射到一个数据字段、功能编号或测试用例。
- 推荐性标准用作设计参考；强制性要求需由团队在正式场景中逐条确认适用性。
- 所有“实时”“自动”“可信”“防伪”“合规”等表述都必须有实现证据，否则降级为“录入”“模拟”或“参考”。
- 先交付可演示的纵向闭环，再扩展统计、导入、IoT 和外部接口。
- 公开查询的信息少于企业内部信息，以数据最小化和可解释性为优先。

## 7. 后续仍需补充的调研

1. 与教师确认课程硬性技术版本、周期、部署和验收形式。
2. 选定 2～3 种代表性冷冻海产品，形成可控的演示字段和温控规则。
3. 获取并阅读适用标准正式全文，完成“条款—字段—功能—测试”矩阵。
4. 访谈至少一名模拟业务角色，验证交接、拆分/合并、拒收和召回操作是否合理。
5. 在原型评审时确认消费者公开字段与企业内部字段的边界。
